# VQ-01 manual run

- Task id: `VQ-01`
- Evidence type: `manual-api`
- Source plan: `internal-docs/plans/a11ied-vitest-command-queue-plan.md#VQ-01`
- Gherkin: `internal-docs/specs/gherkin/17-test-command-queue.feature`,
  scenarios `Commands run in the order they were queued`,
  `Awaiting a command runs everything queued before it`,
  `An awaited failure goes to that await and the queue continues`,
  `An unawaited failure stops the queue`, and
  `A failure keeps its error and starts its stack at the test line`
- Scope: the command queue as a test author reaches it through the built
  `a11ied/test` entry point

## Steps

1. Built the package with `npx turbo run build --filter=a11ied`.
2. Ran a Node script against `packages/cli/dist/test.js` that started
   `queuedScreenReader({ html })` on a checkout page, queued `next('heading')`,
   `checkpoint`, `next('button')`, `expectSpoken`, `expectOn`, and
   `expectSpokenInOrder` without `await`, then awaited `read()`.
3. In the same script, awaited a failing `expectOn({ role: 'link' })`, caught
   it, and called `next()` again.
4. Started a second reader, queued `expectSpoken('Refund')` and `next('button')`
   without `await`, and called `stop()`.

## Observations

- The six queued commands ran in order before `read()` resolved: the cursor was
  on the button, and every check passed.
- The awaited failure went to its `await`, kept its class and `expected`, and
  the queue ran `next()` afterwards.
- The unawaited failure came back from `stop()` as the same
  `ScreenReaderAssertionError` with `exitCode` 4, and its first stack frame was
  line 19 of the script, the `expectSpoken('Refund')` call. The reader was
  stopped before the rethrow.
