## Observed result

- The built CLI exposes `--recording <path>` on the intended command surfaces.
- `doctor` now probes the same native macOS recording path that a11ied actually uses and reports the failure mode clearly for the current host app.
- The real VoiceOver target starts through the built CLI.
- Virtual-target recording still fails explicitly with `recording-target-unsupported`, which is the right behavior.
- Recording-enabled `drive start` now works reliably again. An intermediate regression caused startup timeouts because the new recorder path could reject before `stop()` was called; that is fixed.
- Recording-enabled `drive stop` now returns a specific native-recorder error instead of `driver-broker-timeout`, `session-not-found`, or fake `"completed"` metadata.
- I reran that built-CLI VoiceOver flow after the final lint and standards pass. It still starts successfully, still fails honestly on stop, and still cleans the failed session up instead of leaving broker state behind.
- The current stop error on this machine is:
   - `recording-command-failed`
   - `The native recorder exited with exit code 1 before writing "/Users/mluedke/code/personal/a11ied/output/manual/pd03-drive.mov". Check Screen Recording permission for the current host app.`
- The session is cleaned up after that failure. A follow-up `drive status` returns `session-not-found`, which is correct because the failed stop no longer leaves a stale session behind.
- Direct Guidepup VoiceOver startup works in this app session.
- Guidepup’s published macOS recorder currently shells out to:
   - `/usr/sbin/screencapture -v -C -k -T0 -g <path>`
- Apple’s current `screencapture` man page documents `-g` as “capture audio during a video recording using default input.”
- Because of that, a11ied now uses a native macOS video-only `screencapture` path instead of the Guidepup recorder wrapper on macOS.
- The remaining blocker on this machine is not fake success anymore. It is a real native recorder failure in the current host app session.
